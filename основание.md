MoonshineWiki — разработка с нуля

Ты — основной разработчик проекта MoonshineWiki.

Твоя задача — самостоятельно разработать с нуля рабочее веб-приложение базы знаний MoonshineWiki.

Не ограничивайся планированием или описанием. Ты должен анализировать требования, выбрать простую архитектуру, создать проект, написать код, запустить его, проверить работу и исправлять найденные проблемы.

Проект разрабатывается локально.

Главный принцип

Простота важнее всего.

Это маленькая база знаний, а не enterprise-система.

Не добавляй технологии, абстракции, сервисы и архитектурные слои только потому, что они существуют.

Если задачу можно решить одним простым модулем — не создавай три.

Если для функции не нужен отдельный сервис — не создавай отдельный сервис.

Если достаточно обычной реляционной базы данных — используй обычную базу данных.

Если можно обойтись простым CRUD — делай простой CRUD.

Никакого overengineering.

При каждом архитектурном решении задавай себе вопрос:

««Нам действительно это понадобится в небольшом приложении базы знаний?»»

Если ответ «нет» или «не уверен» — не добавляй это.

Что мы строим

MoonshineWiki — это самостоятельное минималистичное приложение для хранения и просмотра статей базы знаний.

Основной сценарий:

1. Пользователь открывает приложение.
2. Авторизуется.
3. Видит структуру базы знаний.
4. Открывает статьи.
5. Читает их.
6. При наличии прав может создавать и редактировать статьи.
7. Администратор управляет пользователями.

Главное содержимое приложения — обычные статьи.

В базе не будет банковских данных, медицинской информации, сложных бизнес-транзакций или других чувствительных данных.

Поэтому нам не нужна сложная инфраструктура безопасности данных.

При этом авторизация и разграничение прав доступа должны быть реализованы нормально.

Обязательные требования

1. PWA

Приложение должно быть полноценным Progressive Web App.

Оно должно:

- нормально работать на компьютере;
- нормально работать на телефоне;
- устанавливаться на домашний экран телефона;
- иметь app icon;
- иметь manifest;
- иметь service worker;
- корректно работать в мобильном браузере;
- иметь responsive interface.

Приложение должно ощущаться как мобильное приложение, а не как уменьшенная desktop-страница.

---

2. Mobile-first интерфейс

Интерфейс проектируй сначала для телефона.

Desktop — вторичен.

Главные требования:

- минималистичный интерфейс;
- крупные удобные элементы управления;
- нормальные touch targets;
- простая навигация;
- минимум визуального шума;
- хорошая читаемость статей;
- быстрый доступ к поиску;
- удобное редактирование с телефона.

Не нужно делать сложную панель администратора.

Не нужно делать интерфейс похожим на Jira, GitLab или корпоративную ERP.

Нам нужна простая и приятная база знаний.

---

3. Авторизация

В приложении должна быть авторизация.

Минимально необходимы:

- логин;
- пароль;
- выход из системы;
- сохранение авторизованной сессии;
- защита закрытых страниц;
- серверная проверка прав доступа.

Не делай:

- OAuth;
- Google Login;
- Telegram Login;
- SSO;
- LDAP;
- 2FA;
- сложную систему identity management.

Это всё нам сейчас не нужно.

---

4. Пользователи и права

Должны существовать минимум две роли:

Admin

Может:

- создавать пользователей;
- удалять пользователей;
- менять их пароли;
- управлять ролями;
- создавать статьи;
- редактировать статьи;
- удалять статьи.

User

Может:

- входить в систему;
- просматривать статьи;
- искать статьи.

Если понадобится возможность дать обычному пользователю права редактирования, архитектура должна позволять добавить это позже, но не нужно сейчас создавать сложную permission system.

Очень важно

Создавать пользователей может только Admin.

Не делай публичную регистрацию.

На странице регистрации вообще нет необходимости.

Первый администратор должен создаваться во время первоначальной настройки приложения или через переменные окружения / простой setup-механизм.

5. База данных

Используй максимально простую базу данных.

Предпочтительно SQLite, если архитектура приложения это позволяет.

Нам не нужен PostgreSQL только потому, что это «правильнее».

Количество данных будет небольшим.

Основные сущности:

User

Минимально:

- id
- username
- password hash
- role
- created_at

Article

Минимально:

- id
- title
- slug
- content
- created_at
- updated_at
- author_id

При необходимости можешь добавить только действительно необходимые поля.

Не создавай десятки таблиц.

---

6. Статьи

Основная сущность приложения — статья.

Нужны:

- создание;
- просмотр;
- редактирование;
- удаление;
- поиск.

Статьи должны иметь понятный URL.

Например:

"/articles/my-article"

или аналогичный простой вариант.

7. Формат статей

Выбери простой и удобный формат, который позволит писать:

- заголовки;
- списки;
- жирный текст;
- курсив;
- ссылки;
- код;
- цитаты;
- изображения, если это возможно без значительного усложнения.

Предпочтительно использовать Markdown или простой Markdown-подобный редактор.

Но интерфейс для пользователя не должен заставлять его постоянно думать о Markdown.

Если есть возможность сделать простой визуальный редактор поверх Markdown без значительного усложнения архитектуры — можно использовать его.

Главный критерий:

«Статьи должно быть удобно писать с телефона.»

---

8. Структура базы знаний

Нужна простая организация статей.

Не создавай сложную CMS.

Достаточно:

- категории / разделы;
- список статей;
- поиск.

Если для категорий требуется дополнительная простая сущность — создай её.

- knowledge graph;
- автоматической классификации;

9. Поиск

Нужен простой поиск по статьям.

В первую очередь:

- название;
- содержимое статьи.

Не нужен Elasticsearch.

Не нужен отдельный search server.

Не нужен vector database.

Обычного поиска базы данных достаточно.

---

10. Docker

Приложение должно запускаться через Docker.

Цель:

docker compose up -d

После этого приложение должно быть доступно пользователю.

Нужны:

- Dockerfile;
- docker-compose.yml;
- volume для постоянного хранения базы данных;
- volume/механизм для пользовательских данных, если они появятся;
- понятный README с запуском.

Не создавай Kubernetes.

Не создавай Docker Swarm.

Не создавай микросервисы.

Один основной контейнер предпочтительнее нескольких.

Если отдельный reverse proxy действительно необходим — обоснуй это. Но по умолчанию его не добавляй.

12. Безопасность

Нам не нужна enterprise security, но базовые вещи должны быть сделаны правильно.

Обязательно:

- пароли хранить только в виде безопасных хэшей;
- не хранить пароли в открытом виде;
- сервер должен проверять авторизацию;
- сервер должен проверять права пользователя;
- обычный пользователь не должен иметь возможность вызвать admin API напрямую;
- защита от очевидных SQL injection;
- корректная работа с пользовательским вводом;
- корректное управление сессиями.

Не нужно создавать собственный криптографический алгоритм.

Контекст проекта

MoonshineWiki — это специализированная база знаний для людей, занимающихся домашним виноделием, самогоноварением, пивоварением и другими домашними напитками.

Это не просто техническая демонстрация wiki. Нам нужна реально используемая тематическая база знаний.

Поэтому создай при первоначальной разработке небольшое количество демонстрационного контента, чтобы интерфейс сразу можно было оценить как настоящую базу знаний.

Начальная структура

Создай несколько основных разделов, например:

- Самогон
- Вино
- Пиво
- Ингредиенты
- Оборудование
- Рецепты
- Технологии
- Проблемы и решения
- Справочник

Не воспринимай этот список как жёсткое требование. Если после анализа UX ты видишь более удобную структуру — используй более простую и логичную.

Демонстрационные статьи

Создай несколько небольших реальных по структуре статей, например:

Самогон

- Базовый сахарный затор
- Первая перегонка
- Вторая перегонка
- Отбор голов, тела и хвостов
- Разбавление спирта водой

Вино

- Подготовка винограда
- Первичное брожение
- Использование дрожжей
- Снятие с осадка
- Осветление вина

Оборудование

- Перегонный куб
- Дефлегматор
- Холодильник
- Гидрозатвор
- Ареометр

Проблемы

- Брожение остановилось
- Затвор не бродит
- Неприятный запах
- Слишком высокая кислотность
- Низкая крепость

Статьи должны быть небольшими — достаточно нескольких абзацев и примеров.

Не нужно генерировать огромную энциклопедию.

Цель демонстрационного контента — проверить:

- структуру категорий;
- отображение статей;
- поиск;
- навигацию;
- мобильный интерфейс;
- редактор;
- читаемость;
- работу ссылок между статьями.

Визуальный стиль

Тематика может отражаться в визуальном стиле приложения, но очень аккуратно.

Не нужно превращать MoonshineWiki в сайт с огромными картинками бутылок, дубовых бочек и самогонных аппаратов.

Предпочтение:

- чистый;
- современный;
- минималистичный;
- немного «мастерской / ремесленный» характер;
- хорошая типографика;
- спокойный интерфейс.

Приложение должно выглядеть как современный инструмент для хранения знаний, а не как интернет-магазин самогонных аппаратов.

Важное ограничение

Контент нужен прежде всего для демонстрации приложения.

Не трать значительную часть времени на написание энциклопедии.

Сначала должен быть создан движок MoonshineWiki.

Контент можно будет легко добавлять и редактировать непосредственно через интерфейс приложения.
